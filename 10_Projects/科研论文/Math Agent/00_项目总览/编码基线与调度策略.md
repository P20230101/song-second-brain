# 编码基线与调度策略

## 运行原则

文献工作先于写作工作。任何章节 Agent 都只能读取已经进入证据矩阵、并且可以回到原文位置的内容。检索到的题名、摘要或搜索片段只能作为候选线索，不能直接作为正文证据。

系统把每篇文献当作一个需要完成阅读闭环的对象：检索记录 → 原文获取 → 文本解析 → 分段研读 → 结构化文献卡片 → 证据候选 → 证据核验 → 写作可用。阅读闭环没有完成的文献保留在文献库中，但必须带有“仅摘要”“部分全文”或“待核验”状态。

## 文献研读协议

### 第一遍：资料发现与获取

Literature Research Agent 使用 OpenAlex、Crossref、Semantic Scholar 和公开网页扩展关键词，合并重复记录，核对 DOI、作者、年份、期刊和开放全文地址。下载文件保存原始 URL、访问时间和文件类型等必要元数据，不用本地文件标识代替来源核验。

### 第二遍：完整解析

按文献分成标题、摘要、关键词、引言、理论背景、方法、样本、结果、讨论、局限和参考文献等片段。PDF 解析保留页码，网页解析保留标题层级。解析失败或页码缺失时，文献状态不能升级为“已读全文”。

### 第三遍：结构化研读

对每篇可解析文献至少填写：研究问题、理论/概念、研究对象、样本、研究设计、数据来源、分析方法、主要发现、局限、可迁移条件和与当前项目的关系。不要只生成摘要；要分别提取方法证据、结果证据和作者明确的限制。

### 第四遍：证据核验

Evidence Agent 把可写入内容拆成“一个论断 + 一个或多个原文片段”，保存页码/章节、原文摘录、上下文和适用边界。对关键文献或有冲突的论断进行二次复核：第一次由文献研读流程提出，第二次由高精度审查流程裁决。结论冲突时保留两种表述和冲突原因，不强行合并。

### 阅读完成条件

一篇文献只有在以下条件都满足时才标记为 `verified`：

- 已保存可访问的全文或明确记录为只能使用摘要。
- 主要章节完成解析，解析异常有记录。
- 文献卡片的研究问题、方法、结果和局限字段均已填写。
- 进入证据矩阵的每个论断都有原文定位。
- DOI、作者、年份和来源 URL 已通过核对。

## 模型调度策略

运行模型使用配置中的模型 ID，不在 Agent 代码里硬编码。当前默认档位按任务性质分配：

| 任务 | 默认模型 | reasoning effort | 选择原因 |
|---|---|---|---|
| 搜索词扩展、来源发现、批量元数据整理 | `gpt-5.6-luna` | `xhigh` | 文献量大，需要覆盖率和长上下文整理 |
| 网页/PDF 解析、分段摘要、结构化文献卡片 | `gpt-5.6-luna` | `xhigh` | 先完整了解文献，再进入证据抽取 |
| DOI 冲突、重复合并、开放全文判断 | `gpt-5.6-sol` | `high` | 需要在多个来源间做精确判断 |
| 关键证据核验、跨文献比较、理论综合 | `gpt-5.6-sol` | `high` | 需要控制论断范围和处理矛盾 |
| 研究问题、大纲、章节合稿、审稿与定向修订 | `gpt-5.6-sol` | `high` | 需要保持全篇逻辑和目标期刊适配 |
| 标题、摘要、关键词、图规格 | `gpt-5.6-sol` | `high` | 这些内容依赖已确认的整篇论证 |

“Luna 极高”在程序配置中使用官方参数名 `xhigh`；“Sol 高”使用 `high`。`max` 只作为人工指定的重审档位，不作为默认批量任务，避免调度器把所有任务都升级到最高成本。

调度器每次任务都记录：`task_type`、`priority`、`precision`、`context_size`、`source_risk`、`model`、`reasoning_effort`、`token_budget`、`retry_policy` 和 `escalation_reason`。同一任务重试时沿用原模型档位，只有命中明确的升级条件才切换模型。

## 升级和停止规则

- Luna 解析后出现缺页、结构字段缺失、无法定位原文或多来源不一致，升级到 Sol high 复核。
- 文献只能拿到摘要时，保留为 `abstract_only`，不能伪装成全文阅读结果。
- Sol high 无法从原文裁决冲突时，暂停在人工审核节点，要求用户选择保留的研究范围。
- Token 预算用尽时保存检查点和已完成文献，不从头重跑。
- 写作 Agent 遇到证据不足时返回缺口清单，不能用常识补齐引用。

## Harness 与 LangGraph 的边界

Harness 负责任务描述、模型选择、上下文裁剪、Token 预算、文件路径、重试、检查点和人工审核。LangGraph 负责节点顺序、并行分发、条件路由和恢复。调度器不直接生成论文内容，只为每个节点选择执行方案并记录理由。

文献阶段采用“批量发现 → 并行解析 → 逐篇结构化研读 → 关键证据复核”的子图；写作阶段只有在证据门禁通过后才开放。章节之间可以并行，文献阅读和证据核验必须先于章节写作。

## Patch 实施顺序

### Patch 0：接口和状态契约

定义项目输入、`PaperRecord`、`Passage`、`EvidenceClaim`、`TaskSpec`、`RunState` 和产物状态，不接入模型。

### Patch 1：文献检索适配器

实现 OpenAlex、Crossref、Semantic Scholar 和网页搜索的统一接口；完成元数据规范化、去重和来源记录。

### Patch 2：下载和解析管线

加入 httpx、BeautifulSoup、trafilatura、PyMuPDF；保存原始文件、解析片段、页码和解析状态。

### Patch 3：文献研读与证据层

实现分段研读、文献卡片、证据候选、证据矩阵和引用定位检查；在没有模型时用固定样例验证数据流。

### Patch 4：模型调度器与 Harness

实现任务分类、Luna/Sol 档位选择、Token 预算、升级条件、重试、SQLite 检查点和运行日志。

### Patch 5：LangGraph Supervisor 子图

接入资料子图、证据门禁、总编辑规划、章节并行、审稿修订和人工审核节点。

### Patch 6：Obsidian 同步与导出

把文献卡片、证据矩阵、大纲、章节、审稿记录和图件同步到本项目的 Obsidian 目录，生成 DOCX/PDF 初稿。

每个 Patch 都要有可独立验收的产物和最小测试；不把多个阶段的代码一次性堆进一个大改动。
