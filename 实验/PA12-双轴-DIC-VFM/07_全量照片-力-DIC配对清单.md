## 1. 统一配对规则

### 1.1 配对键

每个试验固定使用以下键：

```text
test_id
├── image_sequence        # 图像目录和 JPEG 帧号
├── dic_project            # MatchID 2019 Job.m2inp
├── dic_export             # MatchID CSV（X/Y/E 或 X/Z/E）
└── machine_force_file     # Pos/Speed/Press Excel 或力 CSV
```

`test_id` 优先取图像目录和力文件的共同编号；不能仅根据日期、文件大小或时间长短猜测。力值必须由 `Press.T`（或 XZ 补齐后的等价时间列）插值到 `t_image`，不使用“第 N 张照片对应第 N×10 个力样本”的固定整数规则。

### 1.2 状态含义

| 状态 | 含义 |
|---|---|
| `paired-file-level` | 图像、MatchID 工程/CSV 与力文件按试验编号可以对应 |
| `review` | 文件可以对应，但存在重复、缺帧、ROI、事件边界或轴向命名问题 |
| `force-payload-unreadable` | 压缩包目录有力文件名，但缺失分卷使 Excel 内容不可读 |
| `orphan-force` | 找到力文件，但当前目录没有相同试验的图像序列 |
| `vfm-not-ready` | 尚无共同时间戳/触发号，或首末边界、DIC 质量未通过 |

## 5. 首帧、末帧与破坏事件

### 5.1 统一边界

所有序列都固定记录三个不同概念：

- `frame_reference`：零载/预载稳定参考帧，用作 DIC 基准；
- `frame_first_valid`：力信号离开基线后、仍完整覆盖试样的第一帧；
- `frame_last_valid`：破坏或结束事件后，仍能确认试样状态的最后有效帧。

“文件第一张/最后一张”只是一种候选。末图若已经离开 ROI，只能标记 `out_of_window`，不能命名为破坏终点。

## 6. 为什么现在还不能宣称“照片—力—VFM 已对上”

即便 `JPG` 数量、`m2inp` 帧数和 CSV 唯一帧数相等，也仍缺少下列至少一项时基证据：

1. 相机逐帧时间戳，或相机与 DAQ 的共同硬件触发编号；
2. MatchID 导出的实际帧号与处理时间；
3. 力/位移通道的 `t_machine` 与通道映射；
4. 首帧加载起点、峰值、峰后下降和末帧破坏之间的事件对应。

所以当前每个试验的 `vfm_eligible` 都应先填 `false` 或 `review`，而不是因为名义频率相同就填 `true`。VFM 的最终输入应是：

```text
frame_id, image_file, t_image, trigger_id
    ├── MatchID 2019 3D: U,V,W, strain, correlation/quality
    └── force/position: Fx,Fy,ux,uy = interpolate(t_machine, t_image)
```

### 9.1 当前映射定义

1. 力记录使用 Excel `Press.T` 的实际时间列；当前 XY 文件的名义力传感器频率为 1000 Hz，持续时间和位移使用 `T_end`，不使用 `样本数/1000` 代替时间戳。
2. 首帧锚定到“加载起点候选”：在前 50 个力样本中估计基线，取连续 3 个样本超过 `基线 + max(10×MAD, 5 N)` 的第一个时刻。这样不会把 X-05 的初始回落或 Y-11 的预载卸载误判为加载起点。
3. 末帧锚定到 `Press.T` 最后一个样本；中间图像时刻按帧序号线性插值，力和位移再按时间线性插值。`force_row_left/right` 保留插值两侧的原始行号。
4. Y-11 的记录从高预载开始且没有可识别的上升起点，首帧按 `t=0` 保留，并标记 `estimated_preloaded_start`；这不是把预载伪装成零载起点。

### 9.2 结果边界

这一步完成的是“每张照片均有唯一、可审计的插入力值估计”，不是硬件共同触发意义上的实测同步。当前 JPEG 没有可用逐帧时间戳，也没有相机—DAQ 共同触发号，所以逐帧字段仍为 `t_image_s_est`，全部 `vfm_eligible=false`。取得触发号、相机时间戳或一份可复核的同步事件后，只需替换 `t_image_s_est` 并保留同一 CSV 结构，不能把估计值直接当成 VFM 实测输入。

汇总中的照片数量按实际递归找到的 JPEG 计数；它与部分截图中的 MatchID 输入数不同（例如 X-05 为 165 张 JPEG、130 个 m2inp 帧；X-06 为 133 张 JPEG），差异已保留在汇总 CSV 的 `m2inp_frame_count` 与清单表中，没有删除图片来强行对齐。
