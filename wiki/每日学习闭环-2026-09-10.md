1. 如何依据 [Andrej Karpathy 的 LLM Wiki](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f) 从空 Vault 建立最小知识库。

## 二、今天学到的核心模型

### 1. LLM Wiki 与普通 RAG 的区别

普通 RAG 在每次提问时重新检索和拼接原始资料；LLM Wiki 则把资料编译成持续累积的、相互链接的 Markdown 知识库。后续提问优先读取已经整理好的 Wiki，新的资料再用来修订既有页面、补充交叉引用和标记冲突。

关键转变是：知识不再只存在于一次回答里，而是变成可以继续增长的持久资产。

### 2. 三层架构

```text
Raw sources（原始资料）
        ↓ 读取、提取、比对
The wiki（知识页面、索引、日志）
        ↑ 由 Codex 持续维护
The schema（AGENTS.md 规则）
```

- **Raw sources**：用户提供的文章、论文、摘录、图片或数据。对 Codex 只读，不改写原文。
- **The wiki**：由 Codex 编写和维护的中文 Markdown 页面，保存摘要、概念、主题、比较和综合分析。
- **The schema**：根目录 [`AGENTS.md`](../AGENTS.md)，规定文件职责、摄取流程、查询写回、冲突处理和巡检方式。

当前 Wiki 的入口包括：

- [首页与总索引](../index.md)
- [原始资料说明](../raw/README.md)
- [Wiki 页面说明](README.md)
- [维护日志](../log.md)
- [维护规则](../AGENTS.md)

### 3. 三个基本操作

- **摄取（ingest）**：把一份新资料读入 Wiki，更新相关页面、索引和日志。
- **查询（query）**：先从索引找到相关页面，再综合已有知识回答问题；可复用的答案经确认后写回 Wiki。
- **巡检（lint）**：检查失效链接、孤立页面、矛盾结论、过时陈述和缺失的关键概念。

## 四、今天形成的配置取舍

### 已采用

- Obsidian 作为本地浏览和编辑界面。
- Codex CLI 作为执行整理任务的 AI 入口。
- 标准 Markdown 相对链接，同时兼容 Obsidian、GitHub 和 GitHub Pages。
- GitHub Pages + Jekyll，保持构建链路最小。
- 中文文件名和中文正文，降低日常维护的认知成本。

### 暂不采用

- 不增加向量数据库、RAG 服务、全文搜索或复杂的知识图谱网站。
- 不为了每天的普通整理任务启动子代理；只有需要复杂分析、并行拆解或独立复核时才考虑使用。
- 不把 `.obsidian/`、Cluadian 配置、终端插件资源、Obsidian Base 视图或本机技能目录纳入公开 Wiki。
- Obsidian 终端属于可选能力。当前 [O-Terminal](https://github.com/Quorafind/O-Terminal) 的仓库说明支持 Windows，但社区插件发布状态仍需按当前版本确认；在不需要独立终端面板时，直接使用 Cluadian 调用 Codex CLI 更简单。

## 五、每日学习闭环

每天只需要围绕一个主题运行下面六步：

### 1. 捕获（Capture）

把当天的目标、问题、阅读材料和对话重点写入当天的学习记录。不要只保存“结论”，还要保留问题背景和仍然不确定的地方。

建议记录：

- 今日主题：
- 我想解决的问题：
- 使用的来源：
- 今天产生的关键判断：
- 仍未解决的问题：

### 2. 澄清（Clarify）

让 Codex 先复述目标，再开始整理：

```text
请先用 3-5 句话复述我今天要解决的问题、已有背景和成功标准。
不要立即创建页面；先指出需要补充的上下文和可能的歧义。
```

### 3. 摄取（Ingest）

把公开资料放进 [`raw/`](../raw/)，然后使用明确指令：

```text
请读取 AGENTS.md、index.md，以及 raw/中的这份资料：<文件名>。
按摄取流程提取关键事实、观点、证据、限制和与现有 Wiki 的关系。
先告诉我拟更新哪些页面；确认后再写入 Wiki。
```

### 4. 编译（Compile）

确认写回后，Codex 应完成同一组动作：

1. 更新或创建必要的 Wiki 页面。
2. 为来源性陈述保留可追溯链接。
3. 对冲突结论保留双方来源，不静默覆盖。
4. 更新 [`index.md`](../index.md) 的页面目录和一句话摘要。
5. 在 [`log.md`](../log.md) 末尾追加 `ingest` 或 `query` 记录。

### 5. 复盘（Review）

阅读 Codex 更新的页面，重点检查：

- 是否把来源事实误写成了推断；
- 是否遗漏了限制条件；
- 是否存在与旧页面矛盾的结论；
- 是否有必要增加交叉链接；
- 页面是否真的能帮助下一次学习，而不是只复述今天的聊天。

### 6. 迁移（Carry forward）

把未解决问题转成明天的一个明确入口：

```text
请根据今天的 Wiki 更新，给出明天最值得继续追问的 1-3 个问题。
每个问题说明：为什么重要、需要读取哪些现有页面、可能需要什么新来源。
```

## 六、每日固定提示词

可以把下面这段作为每天开始时发给 Codex 的固定入口：

```text
这是今天的学习整理任务。

主题：<今天的主题>
目标：<我想弄清楚什么>
今天的对话/材料：<粘贴对话摘要或列出 raw/ 文件>

请按以下顺序工作：
1. 读取 AGENTS.md 和 index.md。
2. 区分来源事实、我的判断和仍然不确定的地方。
3. 找出需要更新的已有 Wiki 页面；只有确实形成可复用知识时才创建新页。
4. 先给出整理计划和拟写回的页面，等待我确认。
5. 确认后更新 Wiki、index.md 和 log.md。
6. 最后列出今天新增的知识、发现的冲突和明天的一个首要问题。
```

## 八、今日结论

“第二大脑”的关键不是把更多工具塞进 Obsidian，而是让每天的对话经过固定流程变成可追溯、可链接、可继续追问的知识。当前最小可行闭环已经具备：

```text
提出问题 → 保存来源/对话 → Codex 整理 → 更新 Wiki/index/log → 人工复盘 → 生成下一问
```

先稳定执行这个闭环，再根据真实摩擦决定是否需要终端插件、搜索、自动化或更复杂的工具。
